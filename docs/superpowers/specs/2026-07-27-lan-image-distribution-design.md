# 局域网图片分发中心设计

## 目标

在管理者 Windows 电脑上运行一个局域网图片分发服务。图片只保存于管理者电脑；成员在浏览器登录后只访问本人任务。一张图片是一条任务。系统不使用 SQLite 或其他数据库，状态以原子写入的 JSON 文件和仅追加 JSONL 审计日志保存。

旧 DataGuard 的原始素材、分组、移动均分、Done/返修提交和回收流程不再作为图片分发链路。数据堂质检工具继续承担人工质检、通过和返修操作。

## 已确认约束

- 管理者电脑是唯一服务端与唯一图片存储位置。
- 局域网内使用；成员使用浏览器，不直接挂载原图目录。
- 一张图片等于一条任务。
- 管理者可维护成员名单，指定成员或全选后输入每人数量随机分发。
- 同一图片不得重复分发、重复使用或被后续新图库重新导入。
- 成员只能查看、下载、上传和标记本人的任务。
- 已领取但尚未完成的图片可以先上传，状态为“已上传待质检”。
- 管理者可召回未使用任务；召回须记录原因。
- 日终按成员统计分发、使用、上传、召回、待处理、质检通过和返修数量。
- 质检需要识别图片是否已成功使用；最短边小于 2048 像素、文件夹编号与图片编号不一致时提醒。
- GitHub 推送和发布需另行得到用户确认。

## 方案选择

采用本机局域网 Web 服务：新工具启动后仅监听管理者明确选择的内网地址和端口；成员浏览器访问服务地址。服务端在授权后返回任务图片，不共享原图目录。这样能可靠地实施成员隔离与召回后的访问撤销。

不采用共享盘 ACL 作为唯一权限边界：它无法可靠地阻止本地副本继续处理，且按成员召回和浏览器自动化测试较难统一。

## 目录和持久化

```text
项目根目录/
├─ 图片库/                         # 管理者导入的图片；成员无直接文件权限
├─ 质检项目/
│  ├─ 待质检/
│  ├─ 质检完成/
│  └─ 待返修/
└─ .图片分发中心/
   ├─ config.json                  # 服务、项目根、版本
   ├─ members.json                 # 账号、显示名、密码哈希、启用状态
   ├─ tasks/<task-id>.json         # 一图一任务的当前状态
   ├─ uploads/<task-id>/...        # 成员上传的结果文件
   ├─ audit.jsonl                  # 仅追加审计事件
   ├─ successful-images.jsonl      # 仅追加的成功使用图登记册
   ├─ reports/YYYY-MM-DD.json      # 冻结日终快照
   └─ reports/YYYY-MM-DD.csv       # 人员统计导出
```

所有 JSON 先写入同目录临时文件、刷新后替换；服务端串行处理状态写入，避免同时请求发生重复分发。`audit.jsonl` 和 `successful-images.jsonl` 只追加，不以客户端输入覆盖历史。

## 核心模型

### 成员

`members.json` 中每位成员保存稳定 ID、登录名、显示名、PBKDF2 密码哈希、启用状态和创建时间。身份从会话确定，客户端提交的成员 ID 不参与授权判断。

### 任务

每个 `tasks/<task-id>.json` 保存：

```json
{
  "task_id": "uuid",
  "source_path": "图片库/20260727/a.jpg",
  "source_sha256": "...",
  "perceptual_hash": "...",
  "source_width": 3000,
  "source_height": 4000,
  "folder_number": "12345678",
  "file_number": "12345678",
  "state": "AVAILABLE",
  "member_id": null,
  "assigned_at": null,
  "uploaded_at": null,
  "recalled_at": null,
  "qc_status": "PENDING",
  "version": 1
}
```

状态为：`AVAILABLE`、`ASSIGNED`、`IN_PROGRESS`、`UPLOADED_PENDING_QC`、`QC_PASS`、`QC_REPAIR`、`RECALLED`。状态变化必须保留审计事件和版本号。

## 分发与召回

1. 管理者导入文件夹，扫描每张图片、计算 SHA-256 和感知指纹，写入 `AVAILABLE` 任务。
2. 导入前检查全局任务、成功登记册与活动任务：SHA-256 相同的图片硬性拒绝；感知指纹近似的图片列为疑似重复，须由管理员确认后才能导入。
3. 管理者选择指定成员或全体成员并输入“每人数量”。服务端从 `AVAILABLE` 任务使用安全随机顺序挑选，先写入任务状态，再返回分发结果。任务一经分配，不再参与任何后续抽取。
4. 成员首次下载或点击开始处理后转为 `IN_PROGRESS`；成员可在未完成时上传成果，转为 `UPLOADED_PENDING_QC`。
5. 管理者仅能对 `ASSIGNED`、`IN_PROGRESS` 任务执行召回。召回立即撤销浏览、下载、上传权限，并按策略转回 `AVAILABLE`；已下载副本无法远程删除，该限制在界面和审计中明确显示。
6. `QC_PASS` 任务的源图 SHA-256 与成功成果 SHA-256 写入 `successful-images.jsonl`，后续任何图库导入或成员上传都与该登记册比对。

## 成员隔离与安全边界

- 服务端不把图片库作为 Windows 共享目录公开。
- 每个 API 通过会话身份过滤任务；不能以 URL 中的成员 ID 或任务 ID 越权读取其他成员图片。
- 下载和上传均检查任务归属、状态和版本；召回后令牌立即失效。
- 密码仅以 PBKDF2 哈希保存；首次创建管理员要求更改默认密码。
- 管理端分发、召回、成员变更、统计导出、质检回写都记录操作者、时间、对象、前后状态和原因。
- 服务仅允许绑定私有网段或 `127.0.0.1`，拒绝绑定公网地址。
- 首版不承诺远程擦除成员已经下载的文件；该风险通过最小授权、审计和召回后的服务端撤权控制。

## 质检工具接入

分发中心为已上传任务生成现有质检工具可扫描的目录：

```text
质检项目/待质检/<成员显示名>/<任务编号或任务ID>/
```

每个目录包含原图、上传结果及 `distribution-task.json`。质检工具在扫描或打开任务时读取此文件；质检通过、返修或无效操作写回 `qc-result.json`。分发中心轮询或手动同步该结果，并更新对应任务状态。

质检打开任务时执行：

1. 将源图/成果图 SHA-256 与 `successful-images.jsonl`、其他已通过任务比对；完全相同的成功使用记录显示“重复使用”高优先级提示。
2. 比对感知指纹；近似内容显示“疑似重复”，由质检员决定。
3. 最短边小于 `2048px` 时显示高优先级尺寸提示；提示不替代人工判定。
4. 提取任务目录的完整数字名和图片文件名开头的数字。两者不相同则显示编号不一致；任一方不存在可识别数字则显示“无法校验”。

既有质检规则、通过/返修目录流转和 Excel 报表继续工作；图片分发中心只新增任务元数据和结果同步，不重写质检主流程。

## 日终统计

按本地业务日期冻结可重复读取的 JSON 与 CSV，成员字段至少包括：

- 分发数量
- 已开始使用数量
- 已上传待质检数量
- 已召回数量
- 当前待处理数量
- 质检通过数量
- 质检返修数量
- 精确重复拦截数量
- 疑似重复提醒数量

统计按审计日志和当日状态快照计算，不修改历史快照。

## 验收与测试

### 单元/功能

- 导入时精确重复拒绝、疑似重复提示、合法图入池。
- 指定与全选随机分发时，任务 ID 无重复且数量符合输入。
- 成员 A 不能读取、上传、召回成员 B 的任务。
- 召回后原成员下载、上传均被拒绝；任务可重新分配。
- 未完成任务上传后进入质检队列并能由质检结果同步。
- 新图库中的历史成功图及活动图均被阻止再次分发。
- 日终统计与审计明细逐条相符。
- QC 尺寸、编号、精确重复、疑似重复提醒覆盖正常与边界命名。
- 启动器可安装当前 13,922-entry 运行库；超过 20,000 条目仍拒绝。
- 高 DPI 预览不再受 2560px 上限限制，1:1 仍加载原分辨率。

### 浏览器/安全

- Playwright 使用管理员和两个成员会话完成导入、分发、上传、召回、统计流程。
- 直接更改任务 URL、成员 ID、会话令牌和路径参数均不能读取他人任务。
- 上传路径穿越、恶意文件名、重复提交、过期会话、无权限管理 API 均被拒绝。
- 服务绑定限制、密码不明文、审计追加性和本地 JSON 原子写入均有自动验证。

### 发布门禁

本地完成 Python 单元/功能/浏览器/安全测试和 C# 启动器测试；代码审查工具扫描变更。Windows GitHub Actions 的构建、WPF、打包与自动更新门禁在用户明确确认推送后运行。推送和发布不在本规格确认范围内执行。
